# 数据保留与容量边界

本文说明系统中每类数据的保留期限、清理机制，以及数据量增长后的分区方案。

## 1. 保留策略

清理由 worker 内的保留任务（`src/server/retention.ts`）执行：

- 启动 5 分钟后首次运行，之后每小时运行一次。
- 每次最多工作 30 秒，每条 DELETE 最多删除 2000 行。积压的数据会在后续几次运行中清完。
- 多个 worker 可以同时运行，批次之间用 `FOR UPDATE SKIP LOCKED` 互不阻塞。
- 删除行数记录在指标 `chatbot_retention_deleted_rows_total{table}` 中。

### 用户内容

| 数据 | 保留规则 |
|---|---|
| 会话、消息、制品（Artifact） | 用户删除前一直保留 |
| 已删除会话 | 软删除 30 天后硬删除。消息、生成记录、摘要、检索分块随之级联删除。该会话的制品与对象存储中的文件一并删除（文件仅在没有其他行引用时删除） |
| 用户记忆 | 由 `memoryPolicy.ts` 的老化规则管理（近期记忆 30 天，会话摘要 60 天） |
| 被重新生成替换的回复的检索分块 | 建立索引时删除 |

### 运行与审计数据

| 数据 | 保留期限 | 说明 |
|---|---|---|
| OutboxEvent（已发布或失败） | 7 天 | 仅用于投递 |
| IngressRequest（已结束） | 7 天 | 幂等重试窗口远短于 7 天 |
| BackgroundJob（已结束） | 14 天 | 便于排查后台任务 |
| BusinessOperation（completed 或 failed） | 90 天 | `uncertain` 状态需要人工核对，不会自动删除 |
| ToolRun | 90 天 | |
| AuditLog | 90 天 | 如有合规要求，可在删除前导出归档 |
| UsageEvent 原始行 | 当月加前 3 个完整月 | 更早的数据按"用户 × 月份 × 类型"汇总到 `UsageMonthly` 后删除。汇总和删除在同一条语句中完成，崩溃后不会重复计数 |

### Redis 数据

| 数据 | 保留期限 |
|---|---|
| 生成事件流 | 生成结束后保留 3 分钟（出错或达到长度上限时保留 10 分钟） |
| 快照 | 生成结束时删除 |
| 上下文缓存 | 15 分钟 |
| 配额计数 | 1 小时，以 PostgreSQL 中的数据为准，每小时重新同步 |
| 用户调度队列 | 某用户的队列取空后，立即删除其队列和权重 |

修改保留期限：编辑 `RETENTION_POLICY` 并重新部署。

## 2. 容量边界（单机，约 100 人并发）

| 位置 | 边界 |
|---|---|
| 消息分页 | 每页不超过 2 MiB（`MESSAGE_PAGE_MAX_BYTES`），至少返回一条消息 |
| 分享页 | 每页最多 100 条消息且不超过 2 MiB，通过"加载更多"续读。同一用户访问同一分享，每小时只记一条审计 |
| 会话检索 | 每个进程最多同时执行 4 个检索，排队超过 2 秒即放弃。每次检索有 1.5 秒语句超时，重新生成过滤只作用于候选结果 |
| 负载保护 | API 在以下情况对新请求返回 503，并带 `Retry-After: 2`：事件循环 p99 延迟超过 500 ms（`LOAD_SHED_EVENT_LOOP_MS`），或超过 32 个查询在等待连接池（`LOAD_SHED_POOL_WAITING`）。健康检查不受影响 |
| 流式增量 | 60 ms 或 512 个字符合并为一条 Redis 流记录 |

## 3. 分区方案（暂不实施）

当前数据量下，部分索引加批量删除已经足够。出现以下任一情况时再考虑分区：

- 单表超过约 5000 万行；
- 保留任务连续多次用满 30 秒仍未清完；
- autovacuum 跟不上删除速度（死元组占比长期超过 20%）。

按优先级排列：

1. **AuditLog、UsageEvent**：按 `createdAt` 做月度范围分区。
   - 保留任务改为 `DETACH PARTITION ... CONCURRENTLY` 加 `DROP TABLE`。
   - 两张表都没有被其他表引用的外键，迁移最简单。
   - 迁移方法：建分区父表，复制数据，在维护窗口内重命名切换。
2. **ToolRun**：按 `startedAt` 做月度分区。
   - 它通过外键级联到 Generation，分区后外键仍可保留（PostgreSQL 12 起支持引用分区表）。
3. **Message、MessageChunk**：不建议按时间分区。
   - 它们的访问模式是按会话或用户读取，分区键无法同时满足。
   - 增长主要来自活跃用户，应优先依靠保留策略、已删除会话的清理，以及 pgvector 的 HNSW 索引（单用户分块超过约 5 万时再启用）。

可以借助 `pg_partman` 自动创建和删除分区。
