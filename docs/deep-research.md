# 深度研究（Deep Research）架构方案

本文设计深度研究能力：用户提出一个开放问题，系统用几分钟到几十分钟，从团队数据、文献、内部知识库和网页中收集证据，
产出一份带引用的研究报告。方案从当前架构出发：Worker 与持久队列、Redis 流式事件、Artifact 侧栏、GPAS 工具与身份隔离。
参考的是 Anthropic 和 OpenAI 公开的实现，并复用《[跨样本数据查询](sample-query-data-agent.md)》中的 `data.query`。

---

## 1. 场景与边界

**典型问题**：

- “结合我们团队近半年肠道样本的五星病原检出情况和最新文献，写一份风险研判报告”
- “综述艰难梭菌在宏基因组检测中的检出意义、常见假阳性来源和报告规范”
- “对比我们三个检测项目的病原谱，并给出文献依据”

**和普通对话的区别**：

| | 普通对话（现有智能体） | 深度研究 |
|---|---|---|
| 时长 | 秒级 | 分钟到几十分钟，后台运行 |
| 模型调用 | 一次运行同一时刻最多 1 个，工具调用 ≤ 4 次 | 多个子任务并行，每个子任务几次到十几次工具调用 |
| 数据来源 | GPAS 工具 | GPAS（经 `data.query`）、文献库、内部知识库、网页 |
| 产出 | 一条回复和卡片 | 一份带引用的报告（Artifact），附数据表和来源列表 |
| 触发 | 模型按需调用工具 | 用户确认研究简报后才开始（成本高、耗时长） |

**不在范围内**：诊断建议和任何写操作。报告中注明“仅供科研参考，不构成诊断意见”。

## 2. 参考实现

### 2.1 Anthropic：Research（多智能体编排）

来源：[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

- **编排者–工作者结构**：主智能体先规划，把计划存入外部记忆（上下文超过 20 万 token 会被截断，计划必须单独保存），
  再并行派出 3–5 个子智能体；每个子智能体也并行调用 3 个以上工具。复杂问题的研究时间因此缩短最多 90%。
- **按难度分配投入**（写在提示词里）：简单事实查找用 1 个智能体、3–10 次工具调用；直接对比用 2–4 个子智能体、
  每个 10–15 次调用；复杂研究用 10 个以上分工明确的子智能体。
- **引用专门处理**：最后由一个 CitationAgent 在报告中定位每条论断该引用哪里。
- **通过存储传递产物**：子智能体把成果写入外部存储，只把轻量引用交给主智能体，避免“传话游戏”失真，也节省 token。
- **成本**：智能体约为普通对话的 4 倍 token，多智能体约 15 倍。在 BrowseComp 上，token 用量单独解释了 80% 的表现差异。
  多智能体（Opus 主控 + Sonnet 子智能体）在其内部评测上比单智能体 Opus 高 90.2%。
- **评测**：先用约 20 条真实问题就能看出大的效果差异。用 LLM 评委按事实准确、引用准确、完整性、来源质量、工具效率打分，
  一次调用输出 0–1 分和通过/不通过。人工评测能发现自动评测漏掉的问题，例如偏爱 SEO 内容农场而不是权威来源。
- **生产问题**：运行有状态、错误会累积，因此从失败点继续而不是重来（检查点加重试）；全链路追踪；
  滚动发布（rainbow deployment）避免打断运行中的任务。主智能体同步等待每批子智能体，是已知的瓶颈。

### 2.2 OpenAI：Deep Research

来源：OpenAI 深度研究 API 文档与 cookbook（本环境无法直连 OpenAI 文档站，以下依据官方文档的检索摘要和二手资料，实施前请核对原文）。

- **专用模型**：`o3-deep-research`、`o4-mini-deep-research`，经 Responses API 调用。
- **必须提供数据源**：网页搜索、对向量库的文件检索、远程 MCP 服务器，至少一种。MCP 服务器需要提供 `search` 和 `fetch` 两个工具；
  代码解释器可选。
- **后台模式**：请求可能运行很久，建议使用后台模式，并用 webhook 接收完成通知。
- **研究前的两步**：先由一个轻量模型澄清问题，再把问题改写成详细的研究指令，然后才交给研究模型。
  cookbook 中的 Agents SDK 示例按“分流 → 澄清 → 生成指令 → 研究”组织。
- **安全**：网页或 MCP 结果中注入的指令，可能让模型把私有数据发到外部。官方建议只连接可信的 MCP 服务器，并记录全部工具调用，
  尤其是发往第三方的调用。

### 2.3 本项目取什么

| 取自 | 采用 | 原因 |
|---|---|---|
| OpenAI | 研究前澄清问题，并生成研究简报；后台运行，完成后通知；数据源统一为 `search`/`fetch` 两个接口；私有数据与外部访问分离 | 澄清能减少无效的长时间运行；统一接口让新增数据源只需写适配器 |
| Anthropic | 编排者–工作者结构和按难度分配投入；计划和成果存外部，只传引用；单独的引用核对步骤；检查点续跑；约 20 条问题起步的评测 | 我们没有专门训练过的研究模型，只能靠编排让通用模型完成研究，这正是 Anthropic 的做法 |
| 不采用 | 直接调用 OpenAI 或 Claude 的托管深度研究 | 团队样本数据出境与合规需要单独评估；托管方案的中间步骤不可见，难以接入 GPAS 身份隔离和审计。可以作为以后的一个可选模型来源 |

## 3. 与现有架构的冲突及处理

| 现有约束 | 冲突 | 处理 |
|---|---|---|
| 一个生成槽 = 一个上游许可；`docs/agent.md` 明确禁止在循环中引入并行模型调用或子智能体 | 深度研究需要并行的子智能体 | 新开独立的 **research 通道**，有自己的许可预算（§6），不占用聊天的生成槽 |
| Cookie 加密保存在 `Generation.credential`，生成结束即清除 | 研究持续几十分钟，Cookie 可能过期 | 把 GPAS 数据收集放在最前面、在 Cookie 有效期内完成；结果作为运行内数据集存储（§4.3），后续阶段只读数据集，不再访问 GPAS |
| 业务数据只在 GPAS，本地只保存会话 | 研究过程要保存中间数据 | 运行工作区只在单次运行内使用，按用户隔离、加密存放在对象存储，设保留期（例如 30 天）。最终报告和现在的 Artifact 一样，属于用户自己的产物 |
| 工具调用 ≤ 4 次，单个结果 ≤ 32 KB | 研究需要大量调用和长文本 | research 通道使用自己的上限（§6）；长文本存入工作区，只把摘要和引用交给模型 |
| 聊天 Worker 按会话串行 | 长任务会占住 Worker | 单独的 research Worker 进程，与聊天 Worker 分开扩容 |

## 4. 架构

### 4.1 总体流程

```text
聊天中的智能体
  │ ① 分流：判断是否需要深度研究 → 调用 research.prepare（prepare_confirmation 类工具）
  │    生成研究简报卡片：澄清后的问题、范围、数据源、时间范围、深度、预计耗时
  │    （缺关键信息时先向用户提一两个澄清问题）
  ▼
用户在卡片上确认（与“首次初始化项目”表单相同的确认机制，模型不能自行启动）
  │ 在 Cookie 有效期内创建 ResearchRun，加入 research 队列（持久化，返回 202）
  ▼
research Worker（确定性流程骨架，每个节点内部是智能体循环）
  ② 规划      主智能体读简报 → 输出结构化计划（子问题、数据源、预算）→ 存入 ResearchRun.plan
  ③ 收集数据  先执行团队数据类子任务（data.query），结果存为数据集，然后释放 Cookie
  ④ 并行研究  按计划派出子智能体（有并发上限），每个子智能体上下文独立：
                文献 / 知识库 / 网页 → search · fetch → 写入“发现”（论断、原文摘录、来源 ID）
              子智能体只返回简短摘要和发现 ID
  ⑤ 查漏补缺  主智能体读摘要 → 不足则追加一轮（最多 2 轮）→ 否则进入撰写
  ⑥ 撰写      写作智能体按发现撰写报告；数字和表格由数据集渲染，不由模型书写
  ⑦ 引用核对  为每条论断挂引用 → 确定性校验（§4.5）→ 删除或标注缺少支撑的论断
  ⑧ 交付      报告保存为 Artifact（text/markdown，可多版本），在会话中插入结果消息，通知用户
```

**为什么流程骨架用代码写死、只在节点内部用智能体**：Anthropic 的主智能体可以自主决定派多少子智能体。
在我们的约束下，固定骨架有三个好处：

- 许可和 token 预算可以在每个阶段精确控制；
- 每个阶段结束就是一个天然的检查点，Worker 重启后从最后完成的阶段或子任务继续；
- 规划仍由模型完成，只是以结构化 JSON 输出，由代码执行，便于校验和设上限。

### 4.2 数据源与工具

所有外部数据源都实现同一组接口（与 OpenAI 对 MCP 数据源的要求一致）：

```ts
interface ResearchSource {
  id: 'team_data' | 'pubmed' | 'europepmc' | 'kb' | 'web'
  search(query: string, opts: { limit: number, dateRange?: [string, string] }): Promise<SourceHit[]>  // { ref, title, snippet, url?, publishedAt? }
  fetch(ref: string): Promise<SourceDocument>  // 正文存入工作区，返回 sourceId 和摘要
}
```

| 数据源 | 实现 | 说明 |
|---|---|---|
| 团队数据 | `data.query` / `data.catalog`（见跨样本查询方案） | 唯一的私有数据源。结果是确定性的数据集，带 `asOf` 和口径复述 |
| 文献 | PubMed E-utilities、Europe PMC 的官方接口 | 结构化元数据（PMID、DOI、期刊、年份），优先使用摘要；能取得开放获取全文时再取全文 |
| 内部知识库 | 病原知识、SOP、报告规范等文档。文档量小时直接按目录读取全文；量大时再引入向量检索（当前基线已移除 pgvector 和本地 BGE，需要重新评估） | 非结构化文档适合检索；与“结构化数据不做向量化”不矛盾 |
| 网页 | 可配置的搜索服务，加正文抽取 | 第二期再开放。设域名白名单和优先级（WHO、各国疾控、NCBI 等），降低内容农场的权重 |
| 计算 | 沙箱中执行统计和画图 | 第三期 |

新增数据源只需要写一个适配器，并在注册表中声明，编排流程不需要改。以后也可以把适配器包装成 MCP 服务器。

### 4.3 存储（PostgreSQL 为事实来源，正文放对象存储）

```text
ResearchRun      id, userId, chatId, brief(JSON), depth, status, phase, plan(JSON), budget(JSON), usage(JSON),
                 artifactId, error, createdAt, finishedAt
ResearchTask     id, runId, round, kind(data|literature|kb|web), objective, status, attempt,
                 summary, toolCalls, tokens, checkpoint(JSON)
ResearchDataset  id, runId, taskId, ir(JSON), criteria, asOf, total, objectKey      -- data.query 的结果快照
ResearchSource   id, runId, sourceType, ref, url, title, publishedAt, fetchedAt, contentHash, objectKey
ResearchFinding  id, runId, taskId, claim, quote, sourceId | datasetId, confidence
```

- 子任务之间通过 ID 传递成果（发现、来源、数据集），不传全文，对应 Anthropic 的“通过存储传递产物”。
- 每个子任务完成时提交一次。Worker 崩溃后，从 `status != done` 的子任务继续。
- 工作区对象按 `userId/runId/` 存放，到期删除。审计沿用 `ToolRun`。

### 4.4 智能体角色与提示要点

| 角色 | 模型 | 输入 | 输出 |
|---|---|---|---|
| 分流与简报（聊天智能体内） | 现有模型 | 用户问题与会话上下文 | 研究简报（确认卡片） |
| 主智能体：规划与查漏 | 强模型（`RESEARCH_LEAD_MODEL`） | 简报、各子任务摘要 | 计划 JSON；是否追加一轮 |
| 子智能体：研究 | 轻量模型（`RESEARCH_WORKER_MODEL`） | 单个子问题、数据源白名单、输出格式、预算 | 发现（结构化）和不超过 300 字的摘要 |
| 写作 | 强模型 | 简报、大纲、发现、数据集引用 | 带引用标记的报告 |
| 引用核对 | 轻量模型加确定性校验 | 报告与发现 | 引用映射与问题清单 |

参照 Anthropic 的提示原则：

- 给子智能体明确的目标、输出格式、工具使用指引和边界；
- 把按难度分配投入的规则写进主智能体的提示词；
- 搜索先宽后窄；
- 优先权威来源，并在发现中记录来源类型。

### 4.5 引用与数字校验（确定性）

- **引用存在**：报告中每个引用标记必须对应一条发现，发现必须对应已抓取的来源或数据集。
- **摘录可查**：发现中的 `quote` 必须能在来源正文中找到（规范化空白后做字符串匹配），否则视为无支撑。
- **数字一致**：涉及团队数据的数字和表格由数据集渲染，写作智能体只能引用 `{{dataset:ID.field}}` 这类占位符，
  由服务端替换。这延续了现有的“业务数据只能来自工具结果”规则。
- **无支撑的论断**：标注“未找到依据”，或者删除；在报告末尾列出被删除的论断数量。
- 报告末尾附来源列表（标题、期刊或站点、日期、链接）和数据口径说明（`criteria`、`asOf`）。

## 5. 安全

1. **私有数据和外部访问分离**（针对 OpenAI 文档提示的数据外泄风险）：
   - 读取团队数据的子任务没有网页和外部搜索工具；读取外部来源的子任务看不到团队数据。
   - 主智能体给外部子任务的子问题只能是公开的科学问题。代码会检查外部搜索词，
     出现本团队的样本名、项目编码、文件名或分析 ID 就拒绝执行。
   - 写作阶段才同时看到两类信息，此时已经没有任何外部访问工具。
2. **外部内容一律当作数据**：抓取的正文放在明确的定界符里交给模型，并说明其中的指令无效；正文不进入系统提示词。
3. **抓取防护**：只允许 http(s)；禁止私网和内网地址（防 SSRF，包括重定向之后的地址）；限制大小和超时；
   遵守 robots 和站点条款；文献优先走官方接口。
4. **身份**：团队数据仍用本人 Cookie 经 `data.query` 获取，范围由服务端决定。Cookie 在数据收集阶段结束后清除。
5. **输出**：报告按现有的 Markdown 和 Artifact 安全策略渲染；外部链接加 `rel="noopener noreferrer"`。

## 6. 容量与成本

### 6.1 许可预算

现有不等式加入 research 通道：

```text
GLOBAL_GENERATION_CONCURRENCY + BACKGROUND_CONCURRENCY + RESEARCH_MODEL_PERMITS ≤ UPSTREAM_CONCURRENCY
RESEARCH_MODEL_PERMITS = RESEARCH_RUN_CONCURRENCY × RESEARCH_FANOUT
```

例如 `RESEARCH_RUN_CONCURRENCY = 4`、`RESEARCH_FANOUT = 4` 需要 16 个许可。这时需要把聊天的生成并发从 96 下调，
或者提高上游并发额度。TPM 也要单独核算：按 Anthropic 的经验，多智能体约消耗普通对话 15 倍的 token。

### 6.2 按深度设上限

| 深度 | 子智能体 | 每个子智能体的工具调用 | 轮数 | 抓取页数 | 墙钟时间上限 | 适用 |
|---|---:|---:|---:|---:|---:|---|
| 快速 | 1–2 | ≤ 8 | 1 | ≤ 15 | 5 分钟 | 单一主题的事实汇总 |
| 标准 | 3–4 | ≤ 12 | ≤ 2 | ≤ 40 | 15 分钟 | 对比、带数据的研判 |
| 深入 | ≤ 8 | ≤ 15 | ≤ 2 | ≤ 100 | 40 分钟 | 综述类 |

- 每次运行还有 token 总上限。超出时停止研究，用已有的发现撰写报告，并在报告中注明“因预算提前结束”。
- 每个用户每天的研究次数有限额，在入口处检查（复用现有的按用户调度权重和排队上限）。

## 7. 进度、取消与恢复

- **进度**：沿用 Redis Stream 和 SSE，新增 `research.phase`、`research.task`、`research.source` 事件。
  前端显示阶段、子任务列表、已读来源数，用户可以离开页面，完成后在会话中看到结果并收到站内通知。
  执行步骤沿用 `executionTrace` 的展示。
- **取消**：复用现有的取消接口和取消信号。正在运行的模型调用中止后，已完成子任务的发现保留；用户可以选择“用已有结果生成报告”。
- **恢复**：Worker 租约过期后，其它 Worker 接手，从最后完成的子任务继续，不重复抓取已有来源（按 `contentHash` 去重）。
- **发布**：运行中的任务记录代码版本。发布时旧 Worker 处理完当前子任务再退出，新 Worker 从检查点接手，
  这是 rainbow deployment 的简化版。

## 8. 评测与观测

- **评测集**：先收集 20–30 条真实问题，覆盖三种深度和各数据源；保存参考要点和必须引用的关键来源。
- **LLM 评委**：一次调用，按事实准确、引用准确、完整性、来源质量、工具效率打 0–1 分，并给出通过或不通过。
  评测集固定后再比较改动前后。
- **确定性指标**（每次运行都记录）：引用覆盖率、摘录匹配率、无支撑论断数、数据集数字一致性、token、工具调用数、耗时。
- **人工抽查**：重点看来源质量（是否引用了内容农场、预印本是否标注）和对团队数据的解读是否越界。
- **追踪**：每个阶段和子任务记录输入摘要、工具调用、token 和错误；只记录元数据，不记录团队数据正文。

## 10. 实施顺序

1. **第一期**：快速和标准两档深度；数据源为团队数据、PubMed/Europe PMC、内部知识库；不开放通用网页。
   完成简报确认、检查点续跑、引用与数字校验、Artifact 报告和评测集。
2. **第二期**：开放网页搜索（含 §5 的隔离和抓取防护）；增加深入档；查漏补缺轮次；完成通知。
3. **第三期**：计算沙箱（统计和画图）；把适配器包装成 MCP 服务器；定期研究（例如每周病原监测简报）。

**依赖**：团队数据部分依赖跨样本查询方案中的 `data.query`。在它上线前，第一期可以先只做文献和知识库研究。
