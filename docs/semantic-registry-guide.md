# 语义注册表与 OpenAPI 入门

本文用通俗的方式解释两件事：语义注册表是什么、平时怎么用；上游 GPAS 提供 OpenAPI 需要做哪些事。
完整设计见《[跨样本数据查询](sample-query-data-agent.md)》和《[GPAS 接口语义注册表规划](gpas-semantic-platform.md)》。

---

## 1. 一句话说明

**注册表是一份写在代码里的“说明书”。** 它写清楚：

- GPAS 有哪些数据；
- 每个字段叫什么、中文是什么意思、能怎么筛选；
- 业务上的说法（比如“五星病原”）对应哪个字段的哪个值。

程序和模型都照着这份说明书工作。以后加功能，大多是往说明书里加几行，而不是写一个新工具。

---

## 2. 现在的做法和问题

现在每接一个 GPAS 接口，就要手写一整套代码。以 `file.list` 为例，一个文件有 300 多行：
校验返回格式、挑出给模型看的字段、处理双端重复、写中文说明、写回复格式……

接 10 个接口就要写 10 套，而且每套对“单位”“状态”“团队”的处理可能都不一样。

注册表把这些共性的东西抽出来：**规则只写一次，每个接口只填自己特有的那几行。**

---

## 3. 走一遍例子：“帮我找出有金葡的样本”

| 步骤 | 谁做 | 做什么 |
|---|---|---|
| ① | 模型 | 看注册表的摘要，知道有“样本”和“检出物种”两种数据，检出物种有个字段叫“物种” |
| ② | 模型调用 `data.catalog` | 问“金葡”是什么，字典返回：金黄色葡萄球菌，`taxId = 1280` |
| ③ | 模型 | **填一张查询单**：找样本，条件是有一条检出物种，物种 = 1280 |
| ④ | 程序 | 按注册表检查这张单：字段存在吗？允许“等于”吗？然后翻译成 GPAS 请求，**自动带上当前用户的团队** |
| ⑤ | 程序 | 拿到结果，用注册表里的中文名生成口径说明：“已完成分析的样本中，检出金黄色葡萄球菌的共 12 个”；表格列名也来自注册表 |

**模型只做第 ③ 步，也就是“填单”。** 查字段、翻译、加团队、计数、写口径，都由程序按说明书完成，所以结果稳定、可以检查。

---

## 4. 注册表里写的是什么

一个字段的信息分两处写：**事实**由上游在接口说明书（数据目录）里给出，**含义**由我们在注册表里写。

上游数据目录里的一个字段（上游负责）：

```json
"hazardIndex": { "type": "integer", "range": [1, 5], "ops": ["eq", "gte", "lte"] }
```

意思是：整数，取值 1 到 5，可以按“等于、大于等于、小于等于”筛选。

我们注册表里对应的条目（我们负责）：

```ts
hazardLevel: {
  ref: 'hazardIndex',            // 对应上游的哪个字段
  label: '危害等级',              // 中文名：给模型看，也用于表格列名和口径说明
  synonyms: ['星级', '风险等级'],  // 用户可能的说法
  sensitivity: 'public',         // 可以给模型看
},
```

再加一条业务说法：

```ts
fiveStarPathogen: { label: '五星病原', entity: 'detection', where: { field: 'hazardLevel', op: 'eq', value: 5 } },
```

写完这些，“三个以上五星病原的样本”“每月五星病原检出数”这类问题就都能问，不需要为每个问题写代码。

完整的格式见《[GPAS 接口语义注册表规划](gpas-semantic-platform.md)》§3.2。

## 5. 日常使用的三个场景

**场景 1：上游加了一个字段（比如“采样省份”）**

- 上游在数据目录里给出字段的类型、筛选方式和字典；我们在注册表里加 3 行左右：对应字段、中文名、敏感级别。
- 之后自动生效：模型能按省份筛选和统计，表格能显示这一列，测试模板自动生成。
- 需要人做的，只是补几条真实问法到测试里，比如“广东的样本有哪些”。

**场景 2：业务上出现一个新说法（比如“高危样本”）**

- 在注册表里加一条定义，例如“五星病原 ≥ 1 个，或四星病原 ≥ 3 个”。
- 请业务方确认定义是否正确。不需要写代码。

**场景 3：上游改了字段名**

- 自动检查（CI）报错：“注册表里的 `taxid` 在上游找不到了”。
- 改一行注册表即可。问题在发布前就能发现，而不是等用户提问时才发现答案错了。

## 6. OpenAPI 是什么

**OpenAPI 是一份标准格式的“接口说明书”**，用 YAML 或 JSON 编写，业界通用。它写清楚每个接口的：

- 地址和方法（GET、POST）；
- 需要传哪些参数；
- 返回哪些字段，每个字段是什么类型。

`docs/gpas-project-chat.md` 中的远端验收清单有 18 项待确认，例如：

- `abundance` 是不是百分数？
- `hazardIndex` 的取值范围是多少？
- `taskId` 是不是就是 `analysisId`？

这些问题之所以存在，是因为**上游没有这份说明书**，我们只能猜测，再用真实账号去试。

## 7. 上游需要做的四件事

### 7.1 生成说明书（大部分可以自动完成）

主流后端框架都有现成工具，加一个依赖就能从代码自动生成。例如后端是 Java Spring Boot，
加入 `springdoc-openapi` 后，启动服务访问 `/v3/api-docs` 就能得到。其它框架也有类似工具。

GPAS 用的是什么框架需要向上游确认，可以直接问：“能不能开启 OpenAPI 文档自动生成？”

### 7.2 补上自动生成不了的信息

自动生成只知道“`abundance` 是一个数字”，不知道单位。上游需要在代码注解里补充：

- 单位；
- 取值范围；
- 枚举值的中文含义；
- “团队从登录信息中获取”这类规则。

```yaml
# 自动生成的
abundance: { type: number }

# 补充之后
abundance: { type: number, description: '相对丰度，百分数，0–100', x-gpas-unit: percent }
```

`x-` 开头的是 OpenAPI 允许的自定义字段，用来写标准格式中没有的信息。

### 7.3 放在固定地址，每次发版自动更新

例如 `https://<GPAS 域名>/api/v3/api-docs`。本项目的自动检查每天读取一次，与注册表比对。

### 7.4 修改接口时遵守约定

- 新增字段：随时可以加。
- 改名或删除：提前通知，旧字段至少保留一个版本周期。

### 7.5 上游不需要做的

- 不需要了解本项目的注册表；
- 不需要写“五星病原”这类业务口径；
- 不需要关心 AI 和模型。

上游只负责把**自己接口的事实**写清楚。

## 8. 分工

| | GPAS（上游） | 本项目 |
|---|---|---|
| 写什么 | OpenAPI：接口、字段、类型、单位、范围、枚举 | 注册表：中文名、同义词、业务口径、哪些字段给模型看、用哪种卡片展示 |
| 回答的问题 | 数据**是什么** | 数据**在业务上指什么、怎么用** |
| 什么时候改 | 接口变化时 | 出现新问题、新说法时 |
| 怎么对上 | — | 自动检查注册表引用的字段在 OpenAPI 中都存在 |

---

## 9. 第一步：先做最小的一件事

现有接口的说明书草稿已经起草好，见《[GPAS OpenAPI 规划](gpas-openapi-plan.md)》，上游只需要核对和补全。

不必一开始就讨论完整方案。先请上游**导出现有 6 个接口的 OpenAPI，并补上单位、取值范围和枚举含义**。这一步可以：

1. 消掉验收清单里大部分待确认项；
2. 让本项目开始编写第一版注册表，先迁移 `file.list` 和 `file.result`；
3. 为以后的新接口定下“先提供说明书、再接入”的方式，接入工作只剩下“加声明”。

与上游沟通时可以这样说：

> 我们这边要做 AI 问答，需要准确知道每个接口返回字段的类型、单位、取值范围和枚举含义。
> 能否为现有接口开启 OpenAPI 自动生成，放在固定地址并随版本更新？
> 自动生成不了的单位和枚举含义，麻烦在字段注解里补充。以后修改字段名请提前通知。
