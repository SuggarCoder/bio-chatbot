# GPAS 查询接入方案

本文是 bio-chatbot 接入 GPAS 查询接口的当前方案，取代《[跨样本查询：简化方案](sample-query-simple.md)》。

它要同时满足四个要求：

- **上游工作量小**：不需要 OpenAPI、通用查询语言、数据目录，也不需要改返回格式。
- **查询足够灵活**：任意嵌套的“并且 / 或者 / 非”都能表达，包括带限定的计数（如“细菌里的五星病原 ≥ 3 个”）。
- **结果准确**：总数和分页由上游在一次查询中给出，不在本地拼接。
- **以后接更多接口时，工具数量不变**。

更早的设计（`sample-query-data-agent.md`、`gpas-semantic-platform.md`、`gpas-openapi-plan.md` 等）保留为长期参考。

---

## 1. 总体设计

```text
用户提问
  ↓
模型从 3 个固定工具中选一个：
  user.profile   当前用户与团队
  gpas.query     所有只读查询，用 api 参数指定接口；条件写成条件树
  gpas.prepare   所有写操作，只生成确认表单
  ↓
服务端按“接口注册表”中该接口的那一条：
  校验条件 → 物种名换成编号 → 规范化条件树（把 not 推到单个条件上、补“已完成分析”）
  ↓
上游直接执行约定格式的条件树，按现有格式返回
  ↓
服务端按注册表解析结果，生成口径说明，选择展示方式
```

五条原则：

1. **工具按类别固定，不按接口增加。** 新接口登记到注册表，不新增工具。
2. **每个上游接口在注册表中登记一条**，内容来自与上游约定的一张“接口约定表”。
3. **条件分两种**：样本自身的条件，和“检出条件”（对该样本检出物种的存在、计数要求）。两种条件各自独立，可以自由组合（第 2 节）。
4. **条件树格式由双方事先约定，上游直接执行**。模型写的树和上游执行的树基本一致，本项目只做校验和少量规范化（第 2.3、5.3 节）。
5. **返回格式由上游决定，我们来适配**。双方只约定几条含义上的要求（第 3.1 节）。

## 2. 条件模型

### 2.1 旧设计的两个问题

旧设计中，“未检出”“同时检出”“五星 ≥ 3 个”等都是**按问题预先拼好的固定条件**，导致两类问题表达不了：

| 表达不了的问题 | 原因 |
|---|---|
| “细菌里的五星病原 ≥ 3 个” | `minHazardCount` 把“计数”和“按危害等级筛选”写死在一起，计数的范围只能是“该等级的全部物种”，无法再加“细菌”“丰度”等限定。<br>根本原因是**没有把两层数据分开**：样本（一个样本一行）和检出记录（样本 × 物种，一个样本多行）。所有与物种有关的条件，本质上都是“该样本的检出记录中，满足某些条件的有几条”。旧设计把其中几种组合各写成一个条件，而不是提供一个通用的写法。 |
| “不是（肠道并且五星 ≥ 3）” | 条件组只有一层“组间或者、组内并且”，而且**大部分条件没有对应的否定形式**。按逻辑规则（德摩根定律），“非（A 并且 B）”等于“非 A 或者 非 B”，需要每个条件都能取反；旧设计只有“未检出物种”这一个否定条件。 |

### 2.2 两种条件

**样本条件**：样本自身的字段，如检测项目、样本类型、是否已分析、上传时间。

**检出条件**：一个统一的结构，表示“该样本的检出记录中，满足筛选的物种数量在某个范围内”：

```json
{ "taxIds": ["…"], "hazardLevels": [5], "microbialTypes": ["bacteria"], "minAbundance": 1, "min": 3, "max": null }
```

- 前四项是对检出记录的筛选，都可选，同时出现时取交集；
- `min`、`max` 是数量范围（含两端）。`max` 缺省为不限。`min` 的缺省值取决于是否给了 `max`：没给 `max` 时为 1（即“检出”），给了 `max` 时为 0（如“不超过 2 个”“一个都没有”）。

这一个结构就能表达所有与物种有关的条件：

| 问题 | 检出条件 |
|---|---|
| 检出金葡 | `{ taxIds: [1280] }`（至少 1 个） |
| 未检出金葡 | `{ taxIds: [1280], max: 0 }` |
| 同时检出金葡和大肠埃希菌 | 两个检出条件用 `and` 连接：`{ taxIds: [1280] }`、`{ taxIds: [562] }` |
| 检出金葡、大肠埃希菌中至少一个 | `{ taxIds: [1280, 562] }` |
| 五星病原 ≥ 3 个 | `{ hazardLevels: [5], min: 3 }` |
| **细菌里的五星病原 ≥ 3 个** | `{ hazardLevels: [5], microbialTypes: ['bacteria'], min: 3 }` |
| 四星及以上的病原 ≥ 2 个 | `{ hazardLevels: [4, 5], min: 2 }` |
| 五星病原不超过 2 个 | `{ hazardLevels: [5], max: 2 }` |
| 金葡丰度 > 1% | `{ taxIds: [1280], minAbundance: 1 }` |
| 没有检出任何五星病原 | `{ hazardLevels: [5], max: 0 }` |

以后要加新的筛选维度（如唯一匹配 reads 数、覆盖度），只需在检出条件中加一个字段，所有计数类问题自动可用。

### 2.3 条件树：双方约定的格式

条件树的格式由本项目和上游事先约定，上游直接执行：

```text
节点 = { "and": [节点, …] }        全部子节点都满足
     | { "or":  [节点, …] }        任一子节点满足
     | 条件
     | { "not": 条件 }             该条件不满足；not 只能直接包一个条件

条件 = { "sample":   { 样本条件字段 } }     多个字段同时满足
     | { "detected": { 检出条件字段 } }
```

例如“临床样本中，检出金葡或者细菌五星 ≥ 3，但不包括肠道样本”：

```json
{ "and": [
  { "sample": { "sampleType": ["clinic"] } },
  { "or": [
    { "detected": { "taxIds": ["1280"] } },
    { "detected": { "hazardLevels": [5], "microbialTypes": ["bacteria"], "min": 3 } } ] },
  { "not": { "sample": { "detectionType": ["GUT_MICROBIOME"] } } } ] }
```

**为什么 `not` 只能直接包一个条件**：

- 上游只需要实现“单个条件取反”，不需要处理“对一组条件整体取反”；
- 模型仍然可以对一组条件取反，比如写“不是（肠道并且五星 ≥ 3）”。本项目服务端会按德摩根定律，把 `not` 推到单个条件上，
  变成“不是肠道，或者五星不到 3 个”（第 5.3 节）；
- 这一步转换后，树的大小基本不变，不会像“展开成若干组”那样成倍增加；
- 只要单个条件能取反，加上 `and`、`or`，就能表达任意“并且 / 或者 / 非”的组合。

**和之前被拒绝的通用查询语言有什么不同**：通用查询语言允许任意实体、任意字段、任意运算符，还要配套数据目录和 OpenAPI。
这里只有两种条件，字段都事先约定，只有 `and`、`or`、对单个条件的 `not` 三种组合方式，并且有深度和数量上限（第 3.2 节）。

### 2.4 仍然表达不了的

- **检出记录之间的比较**，如“金葡丰度高于大肠埃希菌的样本”；
- **计数以外的汇总**，如“细菌总丰度超过 50% 的样本”（需要时可以在检出条件中加 `minTotalAbundance`）；
- **跨样本的关系**，如“同一患者 30 天内两次检出”。这需要新的业务对象（患者），属于新接口。

## 3. 与上游的约定

### 3.1 通用约定（所有查询接口都遵守）

| # | 约定 | 原因 |
|---|---|---|
| 1 | 请求结构：`{ ownTeamId, where: 条件树, orderBy, page, pageSize }`，条件树的格式见第 2.3 节。不需要条件的接口可以用 GET 平铺参数 | 所有接口用同一种请求结构 |
| 2 | **校验 `ownTeamId` 与登录会话的团队一致**，不一致返回 403；按 ID 查询时同样校验对象属于当前团队 | 唯一的安全硬性要求 |
| 3 | 返回沿用 GPAS 现有的 `dataPage` 结构 | 上游不用设计新格式 |
| 4 | `totalData` 是符合条件的**业务对象数**，并且是精确值 | 模型会回答“共 N 个”，按文件行计数会给出错误答案 |
| 5 | 每个业务对象只返回一行，并带有它的 ID | 本地去重会让分页和总数对不上；没有 ID 无法“查看详情” |
| 6 | 字段名与本项目一致，不另设对照表 | 模型写的树、本项目发出的树、上游执行的树用同一套名称，调试时一眼就能对上 |

“业务对象”指接口所查的东西，例如样本查询中是样本：双端的两个文件只算一个样本。

### 3.2 上限

| 项目 | 上限 |
|---|---|
| 树的深度 | 5 层 |
| 条件（`sample`、`detected`）总数 | 30 个 |
| 每个 `and` / `or` 的子节点 | 10 个 |
| 每个检出条件的 `taxIds` | 20 个 |
| `pageSize` | 100 |

具体数值可以和上游商量。本项目在发请求前先检查，超过时请用户缩小范围；上游收到超限的请求时返回错误（第 4.5 节）。

### 3.3 每个接口一张约定表

上游每提供一个查询接口，双方填一张约定表。这张表就是注册表的来源，不需要 OpenAPI。

| 项目 | 内容 | 谁填 |
|---|---|---|
| 接口 | 地址、方法 | 上游 |
| 用途 | 一句话说明能查什么 | 双方 |
| 条件 | 每个条件一行：条件名、中文名（同义词）、取值、含义 | 本项目起草，上游确认 |
| 业务对象 | 一行代表什么、`totalData` 数的是什么 | 上游确认 |
| 返回示例 | 一份真实的返回（去掉敏感信息） | 上游 |
| 单位与枚举 | 本项目要显示或计算的字段的单位、取值含义 | 上游，按需回答 |

### 3.4 上游不需要做的

- 不需要写 OpenAPI 或扩展字段，约定表就是文档；
- 不需要支持任意字段、任意运算符，也不需要对一组条件整体取反，只实现第 2.3 节约定的条件树；
- 不需要数据目录、字典接口，也不需要改变现有接口的返回格式。

## 4. 第一个接口：样本查询 `sample.search`

### 4.1 能回答的问题

| 问题 | 条件树（简写） |
|---|---|
| 所有做了肠道微生物检测的样本 | `sample { 检测项目: 肠道 }` |
| 所有检出金黄色葡萄球菌的样本 | `detected { taxIds: [1280] }` |
| 所有鉴定到三个以上五星病原的样本 | `detected { hazardLevels: [5], min: 3 }` |
| 细菌里的五星病原 ≥ 3 个 | `detected { hazardLevels: [5], microbialTypes: [bacteria], min: 3 }` |
| 同时检出金葡和大肠埃希菌 | `and [ detected { taxIds: [1280] }, detected { taxIds: [562] } ]` |
| 检出金葡但未检出大肠埃希菌 | `and [ detected { taxIds: [1280] }, detected { taxIds: [562], max: 0 } ]` |
| 肠道样本，或者检出金葡的样本 | `or [ sample { 肠道 }, detected { taxIds: [1280] } ]` |
| 不是（肠道并且五星 ≥ 3）的样本 | 模型写 `not and [ … ]`，服务端转换成 `or [ not sample { 肠道 }, not detected { 五星, min: 3 } ]` |
| 临床样本中，检出金葡或者细菌五星 ≥ 3，但不包括肠道样本 | 第 2.3 节的例子 |
| 2026 年上传的临床样本 | `sample { 临床, uploadFrom: 2026-01-01, uploadTo: 2026-12-31 }` |
| 在上次结果中再筛临床样本 | 本项目把上次的条件树和 `sample { 临床 }` 用 `and` 连接，再查一次 |
| 肠道和呼吸道样本对比 | 本项目查两次，自己比较两个总数 |

### 4.2 接口与条件

接口：`POST /sample/search`（名称可由上游决定）。它是只读查询，用 POST 是因为条件树放不进 URL。

```json
{
  "ownTeamId": "<会话团队>",
  "where": { "and": [
    { "sample": { "sampleType": ["clinic"] } },
    { "or": [
      { "detected": { "taxIds": ["1280"] } },
      { "detected": { "hazardLevels": [5], "microbialTypes": ["bacteria"], "min": 3 } } ] },
    { "not": { "sample": { "detectionType": ["GUT_MICROBIOME"] } } } ] },
  "orderBy": "uploadTime",
  "page": 1,
  "pageSize": 20
}
```

`orderBy`：`uploadTime`、`analysisTime`（均为降序），默认 `uploadTime`。

**样本条件** `sample`（字段都可选，至少一个；多个字段同时满足）：

| 字段 | 中文名（同义词） | 取值 | 含义 | 确认 |
|---|---|---|---|---|
| `detectionType` | 检测项目（检测类型、检测套餐） | 见第 4.4 节，数组 | 样本的检测项目是其中之一 | |
| `sampleType` | 样本类型 | `clinic`、`media`、`environment`、`lab`，数组 | 样本类型是其中之一 | |
| `analysisDone` | 已完成分析（已鉴定、有结果） | `true` | 分析状态为 `analysisverified` | |
| `sampleName` | 样本名 | 文本 | 样本名包含该文本 | |
| `uploadFrom` / `uploadTo` | 上传时间 | `YYYY-MM-DD` | 上传日期在范围内，含起止两天 | |

**检出条件** `detected`：

| 字段 | 中文名 | 取值 | 含义 | 确认 |
|---|---|---|---|---|
| `taxIds` | 物种 | taxId 数组，最多 20 个 | 只数这些物种 | |
| `hazardLevels` | 危害等级 | 1–5 的数组 | 只数这些危害等级的物种 | |
| `microbialTypes` | 大类 | `bacteria`、`viral`、`fungi` 等 | 只数这些大类的物种 | |
| `minAbundance` | 丰度下限（%） | 0–100 | 只数丰度不低于该值的物种 | |
| `min` / `max` | 数量范围 | 整数；`max` 缺省不限；`min` 缺省时，没给 `max` 为 1，给了 `max` 为 0 | 同时满足以上筛选的不同物种数在范围内（含两端） | |

**未分析的样本**：它们没有检出记录，计数为 0。所以“未检出 xx”（`max: 0`）、“不超过 2 个”、“不是检出 xx”这类条件，
未分析的样本也会满足。本项目在规范化时，给这类条件旁边加上“已完成分析”（第 5.3 节），并在口径说明中写明。
上游不需要理解这条规则，按条件树的字面含义执行即可。

### 4.3 返回

**每行的结构与现有的 `file/dual/merge/list` 相同**（`isPair`、`file1`、`file2`，文件上有 `analysisId`、`briefAnalysis` 等），
只在文件上增加 `detectionType`。这样本项目现有的解析代码和多样本表格都能直接使用。

与 `merge/list` 不同的只有通用约定的第 4、5 条：`totalData` 按样本计数，每个样本只返回一行。

可选字段（有更好，没有也能显示）：

| 字段 | 含义 | 用途 |
|---|---|---|
| `hazardCounts` | 该样本各危害等级的物种数，如 `{ "5": 3, "4": 6 }` | 表格直接显示“五星 3 个” |
| `matchedTaxa` | 该样本中命中条件树里 `taxIds` 的物种 | 表格显示“命中：金黄色葡萄球菌” |

### 4.4 检测项目代码与物种名查询

检测项目代码（上游填写全部取值；第二行只是示例）：

| 代码 | 中文名 | 常见说法 |
|---|---|---|
| `GUT_MICROBIOME` | 肠道微生物检测 | 肠道、肠道菌群 |
| `RESPIRATORY` | 呼吸道检测（示例） | 呼吸道 |

物种名查询（新增）：`GET /species/search?keyword=金黄色&limit=10`，返回 `[{ taxId, taxCnName, taxEnName }]`，要求见第 4.5 节。

### 4.5 对上游的要求

上游怎么实现由上游自己决定，用什么数据库或框架、是否预先计算都可以。只要满足下面的要求，并通过验收用例。

**数据要求**

| 要求 | 说明 |
|---|---|
| 样本有检测项目 | 每个样本都能确定它的检测项目代码（第 4.4 节）。现在没有的话需要新增 |
| 按完整检出结果判断 | 检出条件按该样本**全部**检出物种判断，不能只用 `briefAnalysis` 里的前几名 |
| 检出记录有大类、危害等级、丰度 | 大类的取值与 `microbialTypes` 一致；丰度按百分数（0–100）理解，如果不是请告知 |

**查询含义（必须严格一致）**

1. 结果是本团队样本中，使条件树成立的样本。
2. `and`：全部子节点都成立；`or`：至少一个子节点成立；`not`：它包的那个条件不成立。
3. `sample` 条件：其中每个字段都满足时成立。
4. 同一个字段的多个取值表示“任一”，例如 `sampleType: ["clinic", "lab"]` 表示临床或实验室样本。
5. `detected` 条件：该样本的检出记录中，同时满足全部筛选字段的**不同物种数**在 `[min, max]` 范围内（含两端）时成立。
   缺省值按第 4.2 节；未分析的样本计数为 0。
6. 日期按自然日计算，包含起止两天；请告知使用的时区。
7. `sampleName` 是包含匹配。

**结果要求**

- `totalData` 是满足条件的样本数，必须精确；一个样本只算一次。
- 每个样本只返回一行，带 `analysisId`；行结构与 `file/dual/merge/list` 相同，文件上增加 `detectionType`。
- 排序要稳定：排序值相同时再按 `analysisId` 排序，保证翻页不重复、不遗漏。
- 只返回本团队的样本。

**校验与错误**

- `ownTeamId` 与登录会话的团队不一致时返回 403。
- 以下情况返回明确的业务错误码，并指出出错的位置（如 `where.and[2].not`），不能静默忽略或截断：
  超出第 3.2 节的上限；`and` / `or` 没有子节点；`not` 包的不是单个条件；`sample` 条件没有字段；取值不合法；`min` 大于 `max`。
- 遇到不认识的字段或节点类型要报错，不能忽略。否则条件被悄悄丢掉，结果会比实际多，而且没人发现。

**性能**

- 本项目请求 GPAS 的超时是 10 秒。在团队的实际数据量下，单次查询应明显低于这个时间，建议 3 秒以内。

**验收**

- 本项目提供一组验收用例，每条是一个请求体，加上它在测试数据上应当返回的样本 ID 和总数。
  用例覆盖：每个字段单独使用、`and`、`or`、`not`、多层嵌套、计数的上下限和缺省值（包括 `max: 0`）、未分析的样本、翻页。
- 上游提供一个测试团队和固定的测试数据，或者与本项目约定一份测试数据。

**其它接口**

- 物种名查询（第 4.4 节）：按中文名、英文名包含匹配，最多返回 `limit` 条。
- 现有的 `GET /file/result/list` 需要补上团队校验：`taskId` 不属于当前团队时返回 403。

## 5. 本项目实现

### 5.1 工具

| 工具 | 覆盖 | 说明 |
|---|---|---|
| `user.profile` | 当前用户与团队 | 保持现状 |
| `gpas.query` | 所有只读查询接口 | 用 `api` 参数指定接口，例如 `sample.search` |
| `gpas.prepare` | 所有写操作 | 只生成确认表单，用户确认后才执行（现有 `project.initialize` 的机制）；用 `action` 参数指定操作 |

不管以后接多少接口，工具都是这 3 个，远低于 `AGENT_TOOL_LIMIT = 8`。物种名换成 taxId 在服务端内部完成，不单独占用工具。

### 5.3 `gpas.query` 的参数和处理流程

参数：

```ts
{
  api: string,                 // 接口名，必须在注册表中
  where?: 条件树,               // 支持条件树的接口使用，格式同第 2.3 节，另外允许 not 包任意节点
  params?: 参数,                // 平铺参数的接口使用（如 sample.detail 的 analysisId）
  orderBy?, page?, pageSize?,
  describe?: true              // 只返回该接口的条件清单，不查询
}
```

模型写的条件树与上游格式相同，只有两处放宽：

- `not` 可以包任意节点，例如“不是（肠道并且五星 ≥ 3）”可以直接写成 `not and [ … ]`；
- 物种写名称 `taxNames`，不写 `taxIds`。

服务端处理：

1. **找到接口**：`api` 不在注册表中时，返回接口目录。
2. **校验条件**：按该接口的条件表校验节点、字段和取值。不认识的字段或缺少必填项时，返回该接口的条件清单（中文名和取值），模型据此改正。
   同时检查明显的语义错误，例如 `min` 大于 `max`、取值列表为空、上传日期起晚于止，直接报错，不发请求。
3. **物种名换成 taxId**：调用 `/species/search`。唯一匹配就替换成 `taxIds`；有多个候选时返回候选，由模型请用户选择。
4. **规范化条件树**（纯函数，可单测；树的大小基本不变）：
   1. 把 `not` 往下推到单个条件上：`not and [A, B]` 变成 `or [not A, not B]`，`not or [A, B]` 变成 `and [not A, not B]`，`not not A` 变成 `A`；
   2. 补“已完成分析”：对取反的检出条件，以及缺省值处理后 `min` 为 0 的检出条件，在它旁边用 `and` 加上 `sample { analysisDone: true }`。
      例如“不是检出金葡”变成“已完成分析 并且 不是检出金葡”；
      而“肠道样本，或者检出金葡”不受影响，未分析的肠道样本仍然会入选；
   3. 合并相邻的同类节点，如 `and [A, and [B, C]]` 合成 `and [A, B, C]`；
   4. 检查第 3.2 节的上限，超过时不发请求，请用户缩小范围。
5. **调用上游**：团队取自会话；`where` 就是规范化后的条件树。
6. **解析与检查**：用该接口的解析函数解析，检查行数不超过 `pageSize`。
7. **口径说明**：按模型写的原始条件树（不是规范化后的）用中文名生成，保留用户的原意，并写明自动加上的“已完成分析”。例如：
   “样本类型为临床样本，并且（检出金黄色葡萄球菌，或者细菌中危害等级 5 级的物种数 ≥ 3），并且检测项目不是肠道微生物检测”。
8. **返回**：给模型的是总数、口径说明、精简结果和本次的条件树（用于“在结果中再筛”）；给界面的是该接口的展示方式（如样本表格）。
   翻页由服务端用同一棵条件树重新请求，不经过模型。

### 5.4 模型怎么知道有哪些接口和条件

- **接口目录**：`gpas.query` 的工具说明里列出全部接口，每个接口一行（名称、用途、一两个例句）。
- **条件说明**：接口不多时，直接写在工具说明里；接口多了以后改为按需提供，即第 5.3 节第 2 步的条件清单，或用 `describe: true` 主动获取。
- **写法规则和例子**：放在说明文档（skill）里，按难度给例子：单个条件、`and`、`or`、`not`、带限定的计数、多轮追问。
  另外写清容易出错的规则，如“三个以上”是 `min: 3`，“不超过 2 个”是 `max: 2`，“这些样本里”要沿用上一轮的条件树。
- **工具参数保持通用**（`api`、`where`、`params`、分页），具体条件由服务端按接口校验，工具定义不会随接口增多而变大。

### 5.5 一次请求的样子

用户问：“临床样本里，检出金葡或者细菌五星病原三个以上的，肠道样本不要。”

```text
模型 → gpas.query     { "api": "sample.search", "where": 第 2.3 节的条件树（物种写 taxNames: ["金黄色葡萄球菌"]） }
服务端 → GPAS        GET /species/search?keyword=金黄色葡萄球菌        → 唯一匹配 taxId 1280
服务端                校验条件，规范化条件树（这个例子里 not 已经只包一个条件，也没有需要补“已完成分析”的条件），生成口径说明
服务端 → GPAS        POST /sample/search   第 4.2 节示例中的请求体
GPAS → 服务端        { code: 200, dataPage: { totalData: 9, dataList: [ merge/list 结构的行 … ] } }
服务端 → 模型        { total: 9, criteria: "样本类型为临床样本，并且（……），并且检测项目不是肠道微生物检测", samples: [...] }
模型 → 用户          “共 9 个样本……”，下方是样本表格
```

## 6. 接入新接口的流程

| 步骤 | 谁做 | 内容 |
|---|---|---|
| 1 | 双方 | 填写接口约定表（第 3.3 节） |
| 2 | 上游 | 按通用约定实现接口（第 3.1 节）；需要条件的接口沿用同样的条件树格式和含义（第 2.3、4.5 节），并通过验收用例 |
| 3 | 本项目 | 注册表加一条；返回格式是新的就写一个解析函数；展示优先复用已有组件。条件树的校验和规范化对所有接口通用，不用改 |
| 4 | 本项目 | 加评测用例：这个接口的常见问法，检查模型能选对 `api`、写对条件 |

**不新增工具**。只有两种例外：写操作走 `gpas.prepare` 的表单；文件上传这类有特殊交互的，继续用专用通道。

以后加条件也一样：约定表加一行，上游支持这个字段，注册表加一行。

## 7. 现有工具的迁移

现在有 6 个工具：`user.profile`、`project.progress`、`project.status`、`project.initialize`、`file.list`、`file.result`。按接口逐个迁移：

1. 样本查询一开始就做成 `gpas.query` 的 `sample.search`，不单独建工具；
2. `file.list`、`file.result`、`project.progress`、`project.status` 逐个改为注册表条目。
   `file.list` 中的筛选（文件名、分析状态等）并入 `sample.search`，避免两个接口都能回答“列出样本”这类问题；
3. `project.initialize` 改为 `gpas.prepare` 的一个操作；
4. 全部迁完后，工具从 6 个减到 3 个。

**风险**：

- **最大的风险是条件树格式合法、意思却错了**：`not` 或 `or` 的范围写错、“三个以上”写成 `min: 4`、物种对应错、漏了上一轮的条件。
  这类错误能正常执行，结果看起来合理，用户很难发现；
- 模型从“选工具”变成“在一个工具里选 `api`”，接口之间有重叠时容易选错；
- 条件树比平铺参数难写，格式错误能被校验挡住，但会多一轮调用。

**应对**：

- 每次都在结果上方展示口径说明，让理解上的偏差能被用户看到；
- 评测按执行结果判断对错：把标准答案的条件树和模型写的条件树，分别在一份本地模拟样本数据上执行，比较选出的样本是否相同。
  模拟数据专门包含边界样本（恰好 3 个五星、未分析的样本、只命中一个条件的样本），这样范围和否定上的错误才会暴露；
- 评测按难度分层（单个条件、`and`、`or`、`not`、带限定的计数、多轮追问、应当反问的歧义问题、应当拒绝的问题），每层分别统计；
- 每一步迁移前，先为现有问法（`docs/gpas-project-chat.md` 中的各类说法）和组合问法建立评测基线，迁移后准确率不低于基线再切换。

## 8. 实施顺序

1. **对齐约定**（1–2 次会议）：通用约定（第 3.1、3.2 节）；条件树格式（第 2.3 节）；样本查询的约定表（逐条确认、真实返回示例）；检测项目的全部代码；验收用例和测试数据。
2. **上游**：样本查询接口（条件树）、物种名查询接口、检测项目字段；`file/result/list` 补团队校验。
3. **本项目**：接口注册表、`gpas.query`（含条件树的校验和规范化）、`sample.search` 条目、评测用例和本地模拟数据。
4. **迁移**：按第 7 节把现有工具逐个迁入注册表。
5. **第二期**：样本统计接口 `POST /sample/stats`（请求同样本查询，另加 `groupBy`：`month`、`detectionType`、`sampleType`、`taxId`），
   用于“每月检出 xx 的样本数”“最常见的五星病原”。

## 9. 以后的扩展

- **接口非常多**：单个 `gpas.query` 下的接口超过三十个左右时，按领域拆成几个查询工具（如 `gpas.query_sample`、`gpas.query_project`）。工具数量只随领域增长。
- **新的检出筛选维度**：在检出条件中加字段（如 `minReads`、`minCoverage`），所有计数类问题自动可用。
- **第 2.4 节中表达不了的问题**：按需增加条件（如 `minTotalAbundance`），或作为新接口接入，不引入通用查询语言。
